01 / THE JUDGE

先说清楚判据：两个判分器、四个档位，cc 为什么会被记成 agent 错

这份基准自带一个 judge1，我们另写了一个 judge2。报告的每个数字都依赖这两个判分器的分工和 judge2 的四个档位——不先讲明白，后面的数字都没法读。

1.1 评测是怎么跑的

流程分四步，每一步的产物都会影响最终分数：

步骤做什么输出这一层可能出什么错
1被测 agent 回答 725 道题agent 答案 + 完整输出答错、答偏、超时、拒答
2judge1 粗判（基准自带）对 / 错（二选一）把「表述不同但语义等价」判成错
3judge2 细判（我们自研）四档之一（见下表）档位定义与计分规则脱节
4人工逐条复核本报告复核者的判断本身也有主观性

三个术语在全文反复出现，先固定下来：金标（gold answer）是数据集给出的参考答案；agent 是被评测的智能体；语料是出题所依据的原始对话记录，也就是判断金标对不对的唯一依据。

1.2 两个判分器：一个是基准自带的，一个是我们自研的

这一点必须先说清楚，否则后面所有数字都会读错。上面第 2 步和第 3 步用的是两个完全不同的判分器：

judge1 与 judge2 的分工
judge1 · 基准原判分器judge2 · 我们自研
来历GroupMemBench 基准自带的判分器，随数据集一起发布我们为复核这套基准自己写的，代码在 scripts/judge2.py
输入问题 + 金标 + agent 答案问题 + 金标 + agent 答案 + 语料证据集合
判法语义比对：agent 答案和金标是不是一个意思集合判断：把 agent 引用、按问题检索、按金标检索、按 agent 答案检索四路捞出的语料段落拼成一束证据，看这束证据整体支持谁
输出对 / 错四档：exact / compatible / conflict_gold / conflict_corpus
算出的正确率69.1%74.2%（计分仍按二分类）

「集合思维」是 judge2 的核心设计。它不逐句比对 agent 答案和金标像不像，而是先把「和这道题相关的语料」整体捞出来——agent 自己引用了哪些消息、按问题检索到哪些、按金标检索到哪些、按 agent 答案检索到哪些——形成一束证据，然后只问一个问题：这一束证据整体上站在谁那边？

这么设计带来一个副作用，也是这份报告全部发现的来源：它必须回答「语料支持谁」，就不可避免要判断金标站不站得住。当证据整体站在 agent 那边时，judge2 输出 cc——这个档位的字面意思是「agent 和金标矛盾，语料支持 agent」，实际含义是「这道题的金标有问题」。

关键一句：judge2 没有把「题目错了」当作判分目标，但它把这个东西暴露了出来。

它的设计目标是判「agent 答得对不对」，四档里三档都围绕 agent。cc 本来只是「agent 和金标矛盾时语料站谁」的一个分支，不是为审计基准设计的。但正因为引入了语料这个第三方，它客观上成了一台基准质量探测器——64 次 cc 判定，就是 64 道题的出题问题被顺手照了出来。

反过来说，它也没有能力把「题目错」干净地判出来。cc 只覆盖「语料明确支持 agent」的情况（三条件全满足）；语料沉默、双方都对不上、金标查无实据，它都判不出来，只能归到 cg 或按默认规则信金标。这份报告里那 9 条「金标查无实据」和 8 条「双方都无法判」，就是 judge2 照不到的死角，靠人工复核补的。

1.4 为什么这两个名字容易搞反

cg 和 cc 的前提完全一样：都是「agent 答案和金标实质矛盾」。两个档的唯一区别是语料支持谁。

但名字里的 conflict 指代的对象不一致：conflict_gold 读起来像「与金标冲突」（其实两个档都与金标冲突），conflict_corpus 读起来像「与语料冲突」（其实语料是支持 agent 的）。

更准确的名字应该是 corpus_supports_gold（语料支持金标 → agent 错）和 corpus_supports_agent（语料支持 agent → 金标错）。本报告后文统一用 cg 和 cc，请按上表的实际含义理解。

1.5 cc 的门槛：三条必须同时成立

判据原文对 cc 写得很严，原文是「The bar for this verdict is very high. ALL THREE must hold」：

条件原文中文
(a) at least one explicit passage states the agent's conclusion in substance 至少有一段明确段落，实质陈述了 agent 的结论
(b) that same passage contradicts the gold answer 同一段与金标答案矛盾
(c) the passage answers THE SAME question the user asked (same object, same aspect, same time point) 该段回答的是用户问的同一个问题（同对象、同方面、同时间点）

判据还明确补了一条（第 116 行）：决策语言优先于提议语言。如果金标反映的是早期提议（Proposal:、Suggestion:、should we），而 agent 报的是后来的最终决定（Final:、Locking X、Closing the map with X），应判 cc。

1.6 cc 的定位：它不是判 agent 错，是判题目有问题

这是全文最容易被误读的一处，先说清楚：判分器实际上在做三分类，不是二分类。

判分器的三个出口
出口档位条数判分器在说什么
一exact compatible538agent 答对了
二conflict_gold123agent 答错了
三conflict_corpus64题目有问题，agent 没错

第三个出口是判分器最有价值的地方。它的三条件（见 1.5）设计得很严，一旦满足，就等于宣布：这道题的金标站不住，agent 的答案反而有语料支撑。这不是判分器判错了，是它把出题环节的问题揪出来了。

但要说清楚：这个出口不是为「判题目错」设计的。judge2 的目标始终是判 agent 答得对不对，cc 只是「agent 和金标矛盾时，语料站谁」的一个分支。它把题目问题暴露出来，是集合思维带出的副产品——因为必须去查语料，就不得不回答金标站不站得住。这也决定了它的能力边界：只能照出「语料明确支持 agent」的那 64 道，照不到语料沉默的 9 条和双方都对不上的 8 条，那两类只能靠人工补。

问题出在下一步：计分规则（judge2.py 第 335 行）只认二分类。

"verdict2_binary": "correct" if v2 in ("exact", "compatible") else "incorrect"

只有 exact 和 compatible 算对，cc 被压成了 incorrect。于是：

判分器说：这道题金标有问题，agent 答得对。
计分说：agent 错。

这不是判分器判错，是判分器的第三个出口没接到计分上。63 条本该记在基准账上的错误，被记到了 agent 头上。判分器做了正确的判断，但结论在出口处被丢掉了。

1.8 cg 为什么反而基本准

cg 是「其余全部」的兜底档：所有不满足 cc 三条件、又不属于 exact / compatible 的样本都掉进来。这个集合里混着各种情况——agent 答了别的对象、agent 弃答、agent 超时、agent 答了第三版本。这些 agent 确实错，所以 cg 判「agent 错」在大多数情况下是对的。

逐条核完 123 条后，cg 的内部构成是这样的：

cg 内部实际情况条数金标agent该怎么算
金标站得住，agent 答错94对错算错，判分器判对了
金标站得住，agent 超时未输出8对无输出算错，判分器判对，性质是工程问题
金标在语料里查无实据9无法验证错存疑：判分器按「默认信金标」判了 agent 错
金标被推翻，agent 答对1错对应算对，现在被算错
金标被推翻，agent 部分对3错部分对可辩，本报告两种口径都给了
金标和语料都对不上8无法判无法判题目本身有缺陷
合计123———

关键一点：cg 的 111 条「agent 错」里，94 条金标确实站得住、agent 确实答错。这不是「双方都错」，是判分器正常工作的结果。只有 9 条属于「金标在语料里找不到出处、判分器按默认规则信了金标」——这 9 条才是真正需要打问号的。

1.9 所以判分器该改什么：只差一个出口

必须改：cc 的计分出口

  • 把 cc 从「incorrect」改成「gold_defect」一类，不计入 agent 错
  • 三条件已经确认「语料支持 agent 且反驳金标」，判分器自己的结论就是 agent 没错
  • 改动量：一行代码
  • 效果：正确率从 74.2% 到 83.0%，同时基准问题被单独统计出来

建议改：cg 再拆一档

  • cg 里 8 条其实是「题目本身有缺陷」、9 条「金标查无实据」，和「agent 答错」性质不同
  • 拆出 gold_defect：金标和语料都对不上 → 不计入 agent 错
  • 这样三个出口就完全对齐：agent 对 / agent 错 / 题目有问题
  • cg 的 94 条「金标对、agent 错」保留在 agent 错里，判得对，不动

74.2% 这个数字容易被误读。它不是「agent 只答对了 74.2%」，而是「只有 74.2% 被明确认定为对」。剩下 187 条里，85 条是金标自己有问题或无法验证，另外 102 条是 agent 确实答错。

但反过来也不能说「金标有问题，所以 agent 更强」。金标错和 agent 对是两件独立的事：cc 的 64 条里 63 条 agent 确实对；cg 的 123 条里只有 4 条 agent 对或基本对，其余 102 条 agent 确实答错。详见第三节。

03 / THE REAL 2×2

四档之外：金标 × agent 的真实分布

金标和 agent 各自对错，本来是 2×2 四种组合。原判据只覆盖了其中三种，第四种「金标错、agent 也错」被并进了 cg——但逐条复核后发现，这一档实际是空的。

cc 这一档：判分器立功的地方

  • 门槛高（三条件全满足），能进来的样本几乎都有明确语料支撑
  • 实测 64 条里 63 条 agent 确实答对、题目确实有问题
  • 47 条的理由里，判分器自己写了「corpus supports the agent」「in the agent's favor」
  • 它做对了判断——把出题环节的毛病揪出来了。问题只在计分把这一档压成了「agent 错」

cg 这一档：判得基本对，但有 21 条要分开算

  • 是「其余全部」的兜底档，混着弃答、超时、答偏、答第三版本
  • 实测 123 条里 102 条 agent 确实错（94 条金标对 + 8 条超时）——这部分判得对
  • 漏了 4 条：1 条 agent 全对、3 条部分对，本该进 cc 没进
  • 另有 8 条题目缺陷 + 9 条金标查无实据，混在 agent 错里不合适

「双错」这一档不存在。复核前以为 cg 里装着 111 条「金标错、agent 也错」，逐条核完发现：这 111 条里 94 条金标站得住、agent 确实答错，9 条金标在语料里查不到出处，8 条是超时。真正「金标错且 agent 也错」的一条都没有。

这个发现让基准的账好算多了：金标有问题或无法验证的一共 85 条（11.7%），不是 186 条。

那 9 条「金标查无实据」是怎么判的？judge2 有一条默认规则：证据沉默时，信金标、不信 agent 的弃答。这 9 条里，judge2 的理由原文就写着「the corpus neither confirms the gold… default is to trust the gold」。所以它们不是「金标错」，是「金标无法验证」——出题时可能依据了语料之外的材料（如项目设计文档），而这份语料没覆盖到。

9 条明细：Manufacturing_knowledge_update_15、Technology_knowledge_update_28、Technology_temporal_15、Technology_temporal_29、Technology_term_ambiguity_21 / 22 / 24 / 26 / 30。其中 5 条是术语歧义题，问「某术语对应哪个阶段」，语料里确实没写阶段名。

先排除一个可能的质疑：用来构建语料证据的 msg_node 索引只有 3,886 条，而原始语料有 12 万条，覆盖率仅 3.2%。如果索引缺失导致 agent 引用的消息查不到，复核结论可能站不住。

实测结果：64 条 cc 里 agent 共引用 132 个 msg_node，只有 3 个落在索引之外，0 个在全量语料里不存在。agent 的引用没有幻觉，索引不全不影响结论。

9.4 为什么 cc 会判出这么多题目问题：一个假说

64 条 cc 意味着 64 道题的金标站不住脚。这个比例（8.8%）不算低，值得问一句：这些金标是怎么错的？

一个可能的解释是出题流程本身。如果流程是「先定答案，再构造或筛选语料」，那么出题人心里已经有一个预设答案 X，接下来的工作是围绕 X 组织材料。这个过程里有一个已知的认知陷阱：

白熊效应（ironic process theory，Wegner 1987）：刻意不去想某个念头，反而会让这个念头更频繁地出现。放在出题上——出题人越是提醒自己「语料要围绕 X 写、不要写成别的」，在落笔时反而更容易把「别的」写进去。

结果是：金标是 X，语料里却出现了 Y，而且 Y 往往被写成了更明确的 decision 语言。

这个假说和实测数据对得上：cc 的 63 条里，金标大量停在 proposal 阶段（Propose different anchor:、should we、tentative），而语料里有明确的 decision 语言（Final:、Locking X、DECISION_POINT 标记）。像是「想好了要写 proposal，写的时候却把 decision 写进去了」。

知识更新的 17 条 cc 全部是这一形态，是最集中的证据。

必须说明：这是假说，不是结论。出题过程不在本次复核范围内，无法直接验证。它能解释数据，但也可能有别的解释（比如金标是从早期消息里抽取的，抽取时没往后看）。写在这里是因为它指向一个可操作的改进方向：出题时应该先看完整条时间线再定答案，而不是先定答案再找材料。

9.5 这份复核本身的瑕疵：主持者自查

这一节必须写，否则前面所有结论都会被质疑。

复核者就是实验的主持方。这 187 条不是交给独立第三方核的，是我们自己——也就是设计和运行这套评测的同一方——把题目一条条摊开、对着原始语料看的。

这构成一个明确的利益冲突：复核者有动机把不利结果解释成「题目有问题」，而不是「agent 答错了」。说句难听的，运动员兼裁判。

为什么还是这么做，以及做了什么来限制这个风险：

问题处理方式
没有独立第三方 把每条的判定依据全部摊开：题号、问题、金标、agent 答案、判分器理由、语料原文。任何人都可以拿底稿重核，不同意就指出来
复核者有偏向 有争议的不硬判：3 条部分对、8 条无法判单独列出，不算进任何一边；最终用上下界把不确定性框住，而不是给一个确定数字
方法不精巧 承认这是笨办法——不是设计了一个更聪明的判据，是把 187 条一条条看完。靠的是算力和时间，不是方法论上的优雅
538 条判对的没核 本轮只核了被判为「不对」的样本。如果判分器把答错的判成了对，本报告发现不了。这是明确的缺口
本报告自己就出过错 上一版把 cg 的 111 条「agent 错」整体记成了「金标也错」，把金标问题高估到 186 条。逐条核对金标出处后修正为 85 条。这个错误本身就是「主持者自查」风险的活例证——复核者一旦先有了「基准有问题」的预期，很容易把「agent 错」顺手记成「金标错」

一句话说清楚这个复核的性质：它不是「独立验证」，是「主持方把牌摊开自己查了一遍」。价值在于覆盖全量、每条可追溯；局限在于没有外部视角。

如果要让它变成真正可信的结论，下一步应该是：把底稿交给没参与过这套评测的人，随机抽 30 条重核，看结论能不能对上。这件事还没做。

9.6 判分器表现的小结

做得对的

  • 三分类准确率 97.1%，判「题目有问题」的 64 次全部方向正确
  • 判「agent 错」的 123 次里 102 次正确——且这 102 条的金标都经得起逐字核对
  • cc 的三条件门槛设计得严，没有出现大面积误报
  • 在没有独立验证的条件下，主动去查金标，这是判分器最有价值的设计

做得不够的

  • 出口只有两个，第三个出口（题目有问题）没接到计分上
  • 漏判 4 条：agent 答案里正确和错误成分并存时，只看矛盾部分
  • 8 条题目缺陷被归进 agent 错，性质混淆
  • 9 条金标查无实据时按「默认信金标」判了 agent 错，没有标记为「无法验证」
  • 538 条判对的样本没有反向抽查机制
10 / CONCLUSION

结论与下一步

三个可以定下来的结论

  • 判分器是准的。三分类准确率 97.1%，判「题目有问题」的 64 次全部方向正确，漏判只有 4 条。它不是判错了，是第三个出口没接到计分上。
  • agent 真实正确率 83.0%–84.7%，中点 83.6%。不是 74.2%。但上行空间只有 1.7 个百分点——cg 复核没有推翻结论，只是把区间收窄了。
  • 基准有 85 条金标有问题或无法验证，占 11.7%。其中 64 条 agent 答对了，9 条 agent 也错但金标查无实据，8 条双方都无法判，3 条部分对，1 条出题缺陷。金标错不等于 agent 对，这两件事必须分开说。

要改的其实只有一处

  • 给 cc 一个独立出口。它判的是「题目有问题」，不该计入 agent 错。改成 gold_defect 一类，一行代码。
  • 效果：正确率 74.2% → 83.0%，同时基准问题被单独统计出来，两个账分开记。
  • cg 拆档是建议，不是必须。cg 的 102 条「金标对、agent 错」留在 agent 错里判得对，只是 8 条题目缺陷和 9 条金标查无实据不该混进去。

一句话总结：判分器立了功——它自己揪出了 64 道有问题的题，又准确判出 102 条 agent 真错的答案，只有 4 条漏网。错的是计分出口，不是判分器。把这两个账分开记，才能同时看到两件事：agent 真实水平约 83%，而这份基准有 11.7% 的金标有问题或无法验证。

复核方法

本报告的 187 条结论不是重跑判分器得出的，是人工逐条复核。每条样本的复核依据有四类材料：

材料内容用途
judge2 判定理由判分器给出的完整推理文本看判分器自己认为语料支持谁
agent 引用原文agent 答案中引用的 msg_node 及其原文核实 agent 的证据是否真实存在
金标溯源段落用 BM25 检索金标文本找到的原始消息核实金标是否有出处、出处在哪个阶段
问题阶段锚问题所问的具体 phase 名称判断金标源是否属于被问的那个阶段

判定标准是二维的：金标是否站得住（有无明确段落支撑、是否属于被问阶段、是否被后期 decision 推翻）× agent 是否答对（是否给出金标的值、是否给出语料支持的另一个值、是否弃答）。两个维度交叉得出 A（agent 对）/ B（agent 错）/ C（部分对）/ D（无法判）四类。

本报告的局限

一、复核有主观成分。「金标是否站得住」「agent 是否答对」都需要人判断，边界样本存在争议。本报告的做法是把有争议的 3 条部分对、8 条无法判单独列出，并用上下界把不确定性框住。

二、复核基于已有证据块，不是独立全语料检索。复核使用的是 judge2 已经检索好的证据（agent 引用 + 三路 BM25），没有对 12 万条语料做穷举验证。理论上存在「金标源在语料里但四路证据都没检索到」的情况。

三、错误形态的归类是估算。111 条的五种形态中，「日期算错」和「答了不同对象」两类有交叉，条数为估算值（约 30、约 45），其余三类为精确计数。
